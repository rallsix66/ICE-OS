# ICE v4 历史数据模型 v1

> 2026-10-13。已确认需求：为库存趋势、市场趋势和经营分析保存历史基础，暂不开发复杂分析页面。
> 本文是目标数据合同，尚无新表、历史任务或查询接口实现；不代表已有历史可以完整恢复。
> 配套：[目标架构 v3](architecture-v3.md)、[基础业务模型 v2](database-design-v2.md)、[四源数据流](data-flow-v2.md)。v2 的商品、映射、快照、货票、成本模型继续复用，本篇只补历史必要能力。

## 1. 能回答与不能回答的问题

首期保存并支持未来查询：某日某商品/仓库的实物、可售、锁定数量；某市场的库存及在途变化；来源覆盖/陈旧程度；有成本授权时的已估值小计和覆盖率。所有数字可追到原始批次与业务版本。

库存快照是时点余额，不是出入库流水。相邻快照差不能直接叫销量、销售额、周转率或损耗。市场库存份额也不等于市场销售份额。销售、退货、采购、费用、利润分析需要独立真实来源，当前仅注明扩展接口，不提前建空流水表或编造数据。

## 2. 三层数据与写入所有权

| 层 | 复用/拟扩展实体 | 作用与写入者 |
|---|---|---|
| 原始证据 | `inventory_snapshot_batch`、`inventory_snapshot`、来源货票/轨迹证据 | 来源导入服务发布后不可变；保存原始口径和哈希，不被统计任务改写 |
| 业务历史 | 既有 mapping/binding/cost/receipt 版本；新增商品/Variant/仓库资料版本、货票明细修订 | 对应业务服务追加；当前表/指针只是最新投影 |
| 统计投影 | `history_calculation_run`、`inventory_daily_balance`、`shipment_daily_balance`、受限 `valuation_daily`；市场日统计先用查询视图 | worker 根据已发布事实重算；可重建，不是第二份库存事实 |

`operation_log` 保留谁修改了什么，但不是余额历史或业务事实的替代物。不采用“每天复制全部数据库”或全系统事件溯源框架。

### V5 的库存变化与状态历史如何落地

V5 的 `inventory_change_log` 吸收为可重算的只读差异/解释查询，不新增第二份权威库存台账；`shipment_status_history` 由下述货票/明细修订查询提供，不重复维护另一套状态表。本轮只定义合同，不增加查询实现或无来源流水表。

- 比较先固定前后批次/日统计运行、观测时间、来源范围、商品/Variant/映射、单位及解释方式；同口径已知数量才给差值。未知不是0；跨范围、换绑或单位不兼容时标不可比，不强算一个净变化。
- 返回前值、后值、可空差值、可比性与覆盖/陈旧标记，以及双方事实引用。要区分来源观测变化、资料/映射修订、来源覆盖变化和沿用旧值，不能全部归为真实入库/出库。
- 原因只引用已有、可核验且范围/数量匹配的来源业务凭据、收货证据或批准修订；货票时间接近、API签收、数量恰好相等都不足以证明因果。关联展示不等于已确认原因；无法解释的部分明确“原因未确认”，不编造销售/损耗。
- 货值差异需区分数量、成本版本、汇率、身份和覆盖变化。即使差值明确，也不能直接推导“追加投入”或市场需求增长；暂不新增自动归因算法。证据下钻同样遵守当前市场/仓库和金额权限。

## 3. 统一时间、身份与来源范围

- 技术主键仍为 UUID。历史引用 Variant 和冻结的映射版本后归集 Product，不绕过 Product → ProductVariant；外部 SKU 按来源/账号/仓库/市场限定，编码均为字符串。
- 业务时间 `effective_at` / 来源观测时间 `observed_at` 与系统 `recorded_at`、批次 `published_at` 分开保存，统一 timestamptz/UTC。来源不给业务时间就注明 `time_basis=collector_observed`，不伪造之前的时点。
- 每个统计使用 `calendar_key`（IANA 时区 + 日界线规则版本）、`report_date`、明确的 `period_start_at`/`period_end_at`，区间为左闭右开。不能拿执行服务器本地日期自动分日。
- 建议统一经营日历供跨市场比较，按各市场本地日历的查询必须另带 calendar_key。具体日界线待确认；两种日历的统计不可混加。固定 Demo 时钟不作为正式默认。
- 每个数量字段在一个真实仓库/业务范围和有效期内只有一个权威来源。多个账号重复覆盖同仓不得求和，先确定带版本的来源覆盖规则；未决范围隔离并显示缺口。
- 同一快照以完整仓批次为选点单位，不能为凑齐 SKU 将不同时间的行拼成一个“最新完整仓”。来源删除/缺行语义未确认时，缺行不能自动记零。

## 4. 原始快照与维度版本补充

复用 v2 的批次完整性、行唯一键、映射版本、原始数量和原始证据，不另建第二套 snapshot。

- Batch 补充 `recorded_at`、`time_basis`、`supersedes_batch_id`（纠错时）、`import_kind=live|historical|legacy_baseline`、`parser_version`。相同来源批次键的不同内容仍是冲突，纠错必须形成独立可追溯修订，而非原键覆盖。
- Snapshot 冻结 `mapping_id/version`、`variant_id`、当时 Product 归属证据、单位及资料版本引用。解析失败/缺失不是0，未经确认身份保留外部键和数量，但不进入已确认商品合计。
- 追加 `product_revision`、`variant_revision`、`warehouse_revision`：稳定实体 UUID + revision 唯一；保存业务有效区间、系统记录时间、`supersedes_id`、变更原因。分别记录人工货号/名称/规格/分类/单位，Variant 当时商品归属，以及仓库市场/时区/状态。
- 普通变化只关闭旧有效区间并追加新版本；回溯纠错追加修订，不改旧内容。基于明确 knowledge cutoff 选定的有效解释，在同一实体/业务时点唯一；并发锁/版本检查及数据库约束在实施时一起落实。
- 事实优先保存明确版本外键，不能历史查询时只连接 product/warehouse 当前行，否则改名、归类或迁市场会污染过去。停用对象保留版本和外键，不级联删除历史。

### 两种历史解释不能混用

1. `as_recorded`：使用事实当时冻结的映射/资料/成本及指定系统知识截止时间，重现当时的结果。
2. `restated`：使用有审批和证据的历史修订（包括 v2 的 attribution revision），按指定知识截止时间重算，保留旧结果与修订原因。

当前映射转重核应立即退出当前归集，但不能抹掉过去当时已确认的历史。当前新绑定也不能直接重绑过去的事实；历史重述必须显式批准、带版本并标注。两种解释的统计不能拼成同一条未标记曲线。

## 5. 日库存：`inventory_daily_balance`

一行粒度：一个 calculation_run 中，某日/日历的一个来源账号 + 仓库 + 来源 SKU 的库存时点观测。保留源粒度后再聚合 Variant/Product，可表示未匹配量而不建立假商品。

字段合同：

- `run_id` FK、`source_account_id`、`warehouse_id`、`market_at_observation`、`external_sku_normalized`、`snapshot_id`/`batch_id`（无数据时可空）、冻结的 mapping/Variant/资料版本引用；可空字段必须与归属/质量状态一致。
- `physical_quantity`、`available_quantity`、`locked_quantity`、`source_in_transit_quantity`、`unit`；各自可空，沿用来源口径，source_in_transit 仅作观察，不与飞书在途相加。
- `observed_at`、`age_seconds_at_cutoff`、`quality=fresh|carried|stale|missing|conflict`、`attribution_state`、`selection_rule_version`。沿用昨天数值必须为 carried/stale，显示真正观测时间，不能伪装今天成功采集。
- 唯一键 `(run_id,source_account_id,warehouse_id,external_sku_normalized)`；事实引用必须属于对应仓批次。run 内其他日期/日历不可混入。索引按来源仓范围及 run 建立，日期检索通过 run；正式索引按查询验证。

选点：每仓取业务观测时间在 period_end_at 之前、且系统在 knowledge_cutoff_at 前已成功发布的适用完整批次；同一业务时点的冲突无可靠版本则阻断选点。不得拿明天的快照填今天。未到日终的结果标 provisional，不能冒充日终实测库存。

若当天没新快照，可按批准的时效规则沿用日界线前最近有效批次，但保留缺口标记；从未有数据则 NULL。首次观测前的日期不倒填，未接入仓库通过 scope/覆盖清单表达，不为未知 SKU 生成零行。

库存余额沿时间不可相加：月末取月末选点，日均要注明有效/缺失天数与是否含沿用值。只有同一口径、单位、时间截止和互不重叠范围下，仓库/商品维度才可加总。

## 6. 货票历史与每日在途

复用 Shipment、ShipmentItem、绑定修订和 receipt_evidence；新增 `shipment_revision` / `shipment_item_revision` 保存完整的可解释业务状态，不只依赖日志里的文本。

- 键：`(shipment_id,revision)`、`(shipment_item_id,revision)`；来源输入同时按账号/稳定记录ID/来源版本幂等。多明细修订共享一次业务提交版本，不能发布半张货票。
- 保存 `effective_at`、`recorded_at`、来源版本、市场/目的仓当时值、预计到货、业务状态、有效发货量、累计收货量、单位、映射版本、原因与 supersedes_id。取消、更正、撤销都追加修订。
- 剩余在途按有效版本的发货量减累计收货量，超收/负数拒绝；重复累计收货60仍是60，不再加60。真实发货/收货日期缺失时标未知，不能用首次看到状态的时间冒充准确事件时间。
- `shipment_daily_balance` 一行 `(run_id,shipment_item_id)`，引用被选 revision 和证据，保存有效发货/累计收货/剩余在途、市场/仓库、待核对状态及事实时效；日历、解释方式与 cutoff 来自 run。
- API 轨迹继续独立保存，签收不推进飞书状态；历史在途变化不反向改库存。阶段可能重叠时不能算去重总资产。收货证据也按当时有效版本判断，不把今天补录的确认静默回填到旧报表。

## 7. 历史估值和市场汇总

复用 `product_cost` / `valuation`，补齐系统 recorded_at、成本业务有效期、修订链；汇率有来源、业务日期和版本。过去货值不得乘今天的成本或汇率。

本期估值口径统一为商品成本、不含运费，沿用 [产品货值规则](product-plan-v4.md#货值口径已确认不含运费其余正式口径待确认)。成本版本必须能证明这一口径；不明或含运费的综合成本在澄清前不能进入该估值。将来若批准含运费口径，应另设口径版本，不能覆盖现有历史或把不同口径拼成一条趋势。

- `valuation_daily` 与数量表隔离：一行对应 run 中明确的库存日行或货票日行（恰好一个），引用 cost/FX 版本、计价单位、计价数量、币种、估值日、口径/算法版本和覆盖状态。
- 唯一性为 `(run_id,目标日行,估值口径,报告币种)`；正式 DDL 对库存/货票两种非空引用分别建受控唯一约束，不能用 NULL 比较意外允许重复。
- 成本/数量/汇率缺失或单位不兼容时 amount=NULL；零成本仅在真实批准后合法。保留已估值小计、缺成本数量、未知数量记录数和分母定义；不能从未知数量计算一个假的100%覆盖率。
- 不能简单把各商品覆盖率取平均。比较两天市场份额需同时显示覆盖/陈旧范围，避免把新接仓或补匹配当成真实增长。
- `market_daily_summary` 首期定义为授权查询/视图：按日期、日历、解释方式、统计定义版本、市场、单位、阶段和报告币种分组；拆开国内/海外/在途和质量桶。无金额权限不读取金额底表。
- 市场汇总引用同一计算发布组及其 lineage；下钻必须能还原相同日行和业务版本。跨仓权限必须先筛范围再汇总，不能把全市场预聚合结果发给只获准部分仓库的人。
- 若日后性能需要物化，增加 build/run 版本和依赖清单；原事实仍为权威，可重建，不立即引入统计数据库。

## 8. 计算、补数与修订发布

`history_calculation_run`：`id`、`scope_key`（明确账号/仓库范围集合的规范键）、`calendar_key`、`report_date`、period 起止、`knowledge_cutoff_at`、`interpretation`、`definition_version`、`code_version`、`input_manifest_hash`、`revision`、`supersedes_run_id`、`status=queued|running|failed|published`、provisional 标记、开始/结束/发布时间和非敏感错误分类。

- 同一 `(scope_key,calendar_key,report_date,interpretation,definition_version,revision)` 唯一；相同 scope/日历/日期/解释/定义/knowledge cutoff/输入清单 hash 的重试复用同一逻辑计算，不发布重复日行。更正生成新 revision，保留旧 published run；一次 run 只处理一个经营日，多日重算分别建 run 并记录共同请求ID。
- 输入清单记录批次、业务修订、资料/成本/汇率版本以及缺失范围；子记录提供明确 FK/类型和版本，不能只存无法验证的 JSON。金额依赖信息采用受限访问，不通过通用运行日志泄露成本。
- worker 先生成完整候选结果，再事务发布该组所有日行与运行状态/最新发布指针；失败或部分日行不可见。并发同组采用锁和预期版本检查，旧知识截止/输入水位不能覆盖新发布结果。
- 统计任务由已提交事实的持久化待处理记录/水位驱动；不要只用会丢失的内存回调。崩溃后幂等恢复，业务事实成功而统计失败时显示统计滞后，不把业务事实撤回。
- 晚到批次、历史收货更正、身份/成本修订按受影响业务日期重算。库存沿用值可能影响后续多天，应重算到下一个替代观测/有效版本边界；不能只重算收到数据当天。
- 原样查看旧结果指定 run_id；修订后查询指定解释方式和知识截止，展示修订标记。不可悄悄用现值覆盖旧 published 结果，也不可在同一图线混入多个不兼容口径。
- 补历史必须有原始文件/API时间与内容证据，标记 historical 导入及覆盖范围。现役 inventory 只有最新可售值时，只能导入为有证据的 legacy_baseline，不能扩成连续历史、不能补实物量。

## 9. 最小查询合同（本轮定义，不开发复杂页面）

只读历史服务接受日期区间、calendar_key、商品/市场/仓库过滤、interpretation、definition_version、可选 run/knowledge cutoff 和分页；市场/仓库过滤与当前用户授权求交，不由请求决定权限。

输出业务 DTO：period、维度及其版本、分口径数量、独立金额投影（有授权才返回）、quality、coverage、真实 observed_at、revision/provisional、lineage 引用及统计水位。先鉴权再聚合，禁止返回全量由浏览器裁剪。

历史细项、市场汇总、导出、缓存键、下载文件和日志遵守当前权限。缓存包含权限版本/范围和计算版本，权限撤销后失效；历史有数据不意味着当前用户有权读取。数量只读角色不获取成本、金额排序或推算金额的接口。

## 10. 存储、保留与恢复

- 第一阶段使用普通 PostgreSQL 表和必要复合索引。按“来源SKU/仓数 × 每日批次数 × 留存天数”测算快照行数，统计行数单独测算；达到实际容量/查询瓶颈后再评审分区与归档。
- 分别定义结构化事实、原始文件、统计修订、审计与备份的保留期。保留期限、成本、个人信息处理待确认；未批准前不得沿用同步 artifact 的7天清理来删除历史。
- 统计可以从保留事实重建；若原始文件先归档，保留内容 hash、schema/parser 版本、受控位置和恢复验证。若结构化事实要清理，必须先明确会失去哪段可重算能力，不假称永久可重放。
- 备份覆盖原始事实、修订链、当前/统计指针、身份授权、计算定义和必要对象。备份不等于历史模型，历史表也不等于备份；两者分别恢复验收。
- 不做无来源插值；历史起始日与缺失区间是正式数据质量字段，复杂分析页以后开发也不得掩盖。

## 11. 实施时必须通过的验收

1. 240库存/100在途 → 飞书到货后240/0 → 来源新快照340/0；库存先更新则340/100分列，无收货证据不报440。
2. 同一仓一天多个批次选日界线前完整批次；半页/失败/异常空响应不能发布或把旧值清零。
3. 当日无采集、从未接入、跨时区边界、未来批次、零库存分别可识别；月统计不把每日库存求和。
4. 迟到两天的批次只影响合法业务时点及后续沿用区间；旧 as_recorded 结果仍可重现，新 restated 结果注明修订。
5. 商品改名、Variant换商品、仓库变市场、SKU重绑、成本回溯调整均不悄悄改写旧结果；显式重述可追版本。
6. 重复输入/任务重跑/崩溃恢复/并发重算不产生双份；发布原子，旧运行不覆盖新发布。
7. 只授权一个仓库的人不能读整个市场统计；权限撤销、无金额、导出/缓存/日志以及连接池跨用户均拒绝泄露。
8. 无销售来源时不输出销量、利润或周转率；只迁到最新可售余额时不伪造迁移前趋势。
9. 相邻快照的同量变化不能自动绑定某票或推成销量；换绑/扩仓/陈旧沿用明确标记，缺一端数量时不以0计算差值。
10. 库存/在途估值均不叠加运费；含运费或未知口径的成本不能进入本期估值；成本/汇率修订不覆盖旧版本或伪装成库存增长。

以上是未来实现验收要求，不是本轮已运行的测试结果。
