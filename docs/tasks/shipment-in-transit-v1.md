### 1.1 原表列（A–J 有表头；K–T 空）

`A 产品`、`B 数量`、`C 国家`、`D 报关方式`、`E 运单号`、`F 采购单号`、`G 物流情况`、`H 预计到货时间`、`I 船名`、`J 发出时间`。

- **无 SKU 列、无单位列、无到货数量列、无独立“备注”列**（已读全 20 列，K–T 无表头无数据）。本包**不新增备注输入**。
- `数量` 是**发货数量**（用户 2026-11-01 明确：数量就是发货数量）。
- `G 物流情况` **只填写运输进度**（已发出/离港/清关/拆柜/派送/转运/查验/预计到港 等），可带日期，也可能是某个运单的进度（如 `88035948/88035949 10/30待装柜`）。**G 不承担到货/上架判断**。
- `H 预计到货时间` 用来写：预计日期、`时间待定`、**分批到货**（`…已到105件，余40件未到`）、**已到未上架**（`已到货，待上架`）、**已到已上架**（`已到货上架`）；一票多运单时按运单逐条写，也可按商品写（`三酸喷雾：已到货上架`）。**到货/分批/上架判断只依据 H。**
- 两列描述的事实可能不一致（例如 G 仍写 `清关中`、H 已写 `已到货上架`）：**以 H 为准**，不要求用户清空 G，也不报两列冲突。

### 1.2 一票多商品与同票字段

- 原表用**合并单元格**表示“一票多明细”：同一票的 C–I 列在首行填值、其下各产品行留空（合并区）。77 个合并区覆盖其中 11 票；其余票是单行或未合并，但仍是“首行有国家、其下连续产品行”的结构。
- 实测分组规则（与既有日常处理链一致）：`C 国家` 有值的行是**新票首行**；其后的行在出现下一个“国家非空行”之前都属于同一票，票级字段从首行向下沿用。
- 当前 37 票：最多 14 条明细、最少 1 条；86 条明细全部有产品名和正整数发货量。
- **同票重复 SKU**：当前 37 票内没有同一产品名重复；数据模型仍按“同票同产品名可重复”处理（按出现次序区分明细，不合并）。
- `运单号` 可能多张（换行或 `/` 分隔），也可能为空；`采购单号` 可能为空。**两者都空**的票是“弱身份票”（编号列没有可辨识信息）。

### 1.3 跨次识别与身份延续（本轮纠正 R1）

**内部身份 = 数据库 `catalog.shipment.id`（UUID），永不随采购单号/运单号变化。** 每次读取由服务端按下列优先级把本次票匹配到已有票：

| 优先级 | 依据 | 结论 |
| --- | --- | --- |
| P1 | 采购单号（去空格、大小写不敏感）与某张已有票相同 | 唯一 → 延续该票 |
| P2 | 运单号任一 token 与某张已有票相同（多运单票按任一重叠） | 唯一 → 延续该票 |
| P3 | 该票历史既无采购单号也无运单号（弱身份票），且 市场 + 报关方式 + 规范化品名集合 与某张已有票完全一致（该票本次**没有**以弱身份票再出现） | 唯一 → 延续该票（补号） |

- 匹配到原票 → **沿用原票与明细的 UUID、商品关联、修订链**；只更新编号/字段，`采购单号`/`运单号` 的变化记入该票修订历史（页面可看到“采购单号 A→B”）。
- 补采购单号、修改已有采购单号、无单号时补运单号：只要原票的运单号或弱身份特征仍在，**结果都是原票显示新编号，票数不变、关联不丢**。
- **不能唯一确认时不猜**：候选多于 1 个、P1/P2 证据指向不同票、或只能靠弱信号（无运单号且改采购单号）确认时 → 新建行并标 `identity_status='pending'`（页面「身份待核」+ 原候选说明）。这类行**不是**“正常在途记录”，需人工核对；不静默合并，也不静默重复。
- 续接后身份回到 `confirmed`（指**真正按 P1/P2/P3 依据续接到原票**的情况）；`identity_status` 变化同样进修订历史。
- **待核只能由真正解决身份疑问的依据或明确核对结果解除**：已有 `pending` 记录被正常重读（同内容刷新、G/H 变化、数量变化、其它业务字段更新）只说明“继续更新这一行”，不证明它与原候选票的关系已核清；服务端必须原样保留同一 UUID、`pending` 与原候选说明，不自动改 `confirmed`、不清空说明。本轮不新增自动解除路径，也不新增人工核对工作流（如实列为限制）。
- 明细级身份不变：`<规范化品名>#<同票内序号>`；品名改名视为一条退出 + 一条新增（保留原记录与关联）。
- 已知不可自动确认（如实保留）：同时改编号又改品名/市场/报关方式；无运单号且改采购单号（弱证据）。这些情况标「身份待核」，不猜。

### 1.4 状态口径（用户 2026-11-01 第二次确认；本轮纠正 R3）

- **G 独立展示运输进度；到货/分批/上架判断只依据 H**，不把 G 与 H 拼接判断。
- `已到货上架` 表示**整票已到并已上架（已加进 BigSeller 库存）**，结束对应在途。
- `待上架` 尚未结束本包在途（沿用用户现有日常口径）。
- H 为空或只有预计日期/`时间待定`/运输进度时：**不当作实际到货**，继续显示 G 的运输进度，业务状态按在途。
- H 只说明某个商品或某张运单已到（带品名/运单号等限定语）→ 只算部分到货，**不能当作整票已到**。
- 无法确定逐条到货数量时显示「未提供」+ 待核，不猜数量，也不从自由文本抽数字。

| 分类（状态标签） | 判定（只看 H；G 只作展示） | 累计到货 | 剩余在途 |
| --- | --- | --- | --- |
| `arrived` 已到货上架 | H 的到货说明是**整票**已到货并已上架（不带品名/运单号/分批/待上架限定语） | = 发货量（依据：整票状态） | 0 |
| `arrived_pending_shelving` 已到货待上架 | H 说明整票已到但未上架（`已到货`/`待上架`，无分批/未到/单条限定语） | 0（依据：尚未上架、未结束在途） | = 发货量 |
| `partial` 部分到货待核 | H 出现分批/部分/已到 N 件/余 N 件未到，或到货说明带品名/运单号等限定语（只到一部分） | 未提供（NULL） | 未提供（NULL），标待核 |
| `in_transit` 运输在途 | H 没有任何到货信息，或只有预计日期/待定/运输进度 | 0（依据：状态非到货） | = 发货量 |
| `unknown` 状态未提供 | H 与 G 都没有可判断状态的内容 | 未提供（NULL） | 未提供（NULL），标待核 |

- 数量规则：`剩余在途 = 发货量 − 累计到货`；只有两者都已知才出数字；未知不写 0。
- 若来源将来提供逐条到货数量（`累计到货量` 列），入库后自动按 `发货量 − 累计到货` 计算；重复读到同一累计值不累加（按快照覆盖）。
- 状态与数量矛盾（H 同时写已到货上架与余 N 件未到、或同票部分运单已上架部分待上架）→ `partial`，标待核，不猜、不归零。

### 1.5 来源移除口径（本轮纠正 R2）

- 一次**成功且内容有变化**的完整读取后，原表不再出现的票/明细：
  - 退出**当前**列表、状态/市场/关键词计数、关键词与商品筛选结果、商品库「相关货票」；
  - **保留**历史事实、原数量/状态/关联与最后一次来源出现时间，并明确显示「本次来源未见」；
  - **不**自动当成已到货，**不**把数量改成 0，**不**删除行、**不**删除关联。
- 判断“当前”的依据是**最近一次成功读取的快照**（`last_seen_snapshot_id = 最近成功快照`），不是各行自己的最后时间；因此“部分票消失”与“整票消失”口径一致。
- 列表默认只显示当前存在的票；可切换「包含本次来源未见」查看历史行（行上标「本次来源未见」，详情保留原时间）。
- 详情中的当前明细与历史明细分开展示：当前明细可编辑关联；历史明细只读（保留原关联与最后出现时间）。
- 内容未变的重复读取、读取失败：**不能**误使现有整批退出（未变直接返回，失败不写业务数据）。

## 3. 数量与库存边界

- 发货不扣国内库存；到货不增加海外/国内库存；海外库存继续由 BigSeller 决定。本包不计算跨阶段去重总量/总资产。
- 不同单位不合成总件数：当前来源无单位列，列表/详情只做**逐明细**数量与「明细条数」，不显示跨明细合计数量。
- 只读关系：本包的读写只落在 `catalog.shipment*` 新表；不写 `inventory*`、`item_current/item_revision`、`inventory_sku_mapping`、国内快照。

## 5. 读取链路与失败恢复

1. 页面「刷新」触发服务端动作：`lark-cli` 读 wiki 节点 → 表信息 → 区间值（服务端入口一次校验表头/行数/revision）。
2. 解析成明确类型（票/明细分组、H 到货分类、数量口径）→ 读身份索引 → 匹配结论 → 调用 `ingest_shipment_snapshot` 单事务写入。
3. 成功：更新当前投影、追加有变化的修订、记录本次读取时间；页面显示本次结果（新增/更新/未变/本次未见/票数与明细数）。
4. 失败：写入失败快照（错误码/原因/时间），**不写业务数据**；页面继续展示上一份有效数据与原来源时间，并给「重试」入口。不把失败、未提供数量、未关联显示成 0。
5. 再次读取同一票同一明细：更新同一行（不重复生成票/明细），变更进历史；内容哈希未变直接返回 `unchanged`。

## 6. 商品关联

- 自动关联只做**明确唯一**：规范化品名与商品库标准名完全一致且只命中 1 个商品时标记 `auto`。名称相近、命中多个、含别名但未确认 → 不自动关联。
- 其余明细保留原品名/发货量/状态/备注，`associationStatus='none'`，管理员在详情内搜索商品库（货号/名称/条码）选择并保存，`manual`；可更换或清除，均追加历史与修订。
- 编号变化延续原票时**关联不丢**（关联挂在明细 UUID 上）；来源移除的历史明细保留原关联，但不再参与当前「相关货票」查询。
- 关联只影响货票明细归属，不改 BigSeller/聚水潭库存绑定，不改商品资料。
- 商品详情提供「相关货票」入口：跳到 `/dashboard/in-transit?product=<itemId>`。

#### 22.1 原因

`src/features/inventory/components/inventory-detail-layer.tsx` 打开详情时先把 `pushedRef.current` 标为 true，再 `router.push(detailHref)`；App Router 要等路由/RSC 完成才把详情地址写入历史栈。用户在这个窗口内关闭时，`close()` 看到 `pushedRef=true` 就执行 `router.back()`，而此时详情地址尚未入栈，于是退到真正的上一页（从数据同步进入时即数据同步页）。

#### 22.2 修复（仅 1 个文件）

- 打开详情改为只登记 `pendingNavRef`（`itemId/rowKey/cancelled`）并发起 `router.push`；只有页面 props 的 `query.item/query.row` 真正变成该详情地址后，effect 才置 `pushedRef=true`（已提交）。
- 地址未提交时关闭：标记本次导航 `cancelled` 并 `router.replace(listHref)` 覆盖回列表；若原导航仍落地，提交后的 effect 立即 `router.back()` 退回列表。快速关闭既不会 back 到上一页，也不会把地址停在详情。
- `close()` 同步读取当前 URL 决定分支：详情地址已提交（或确实已入栈）才 `router.back()`；直接打开详情链接与地址未提交时走 `router.replace(listHref)`。
- popstate 回到无 `item/row` 地址时清空导航标记并关闭弹层（原有后退关闭行为保留）。
- 未使用延迟关闭、禁用关闭按钮、等待加载或新增导航框架；R15 的固定尺寸、页签与业务内容未改。
