# ADR-ICE-002：脱离 Supabase 与历史数据底座

- 日期：2026-10-13。
- 状态：方向 accepted；具体实现、环境迁移与生产切换未执行。
- 决定依据：用户明确要求脱离 Supabase，并在 ICE v4 基础上增加历史数据能力，暂不开发复杂分析页面。
- 部分取代：[ADR-ICE-001](ADR-ICE-001-identity-snapshot-boundary.md) 中“Supabase 作为后续开发默认平台、退出仅为未来选项”的方向；商品身份、四源权威、Demo 隔离和迁移安全边界继续成立。

## 决定

1. 目标为不依赖 Supabase 服务的标准 PostgreSQL + 自有服务端。自托管整套 Supabase 不算完成退出。
2. 推荐复用当前 Next.js/TypeScript 服务端和 Repository，逐模块替换 SDK/PostgREST/Auth/后台 service-role 路径，不另起一个全量重写项目。具体认证组件、数据库版本及部署位置需在实施前确认。
3. 从第一个新来源批次开始保留不可变快照与业务版本；日统计是可重算投影，不是另一份库存权威。
4. 历史必须区分业务发生时间、系统收到时间和修订时间；保留当时商品归属、市场、单位、成本、汇率和计算口径。
5. 本轮只更新架构、模型、数据流与规则入口；不建表、不接真实数据、不迁移账号、不切生产、不开发复杂分析页。

## 理由与取舍

用户要求自主掌握数据库、认证和历史数据。继续默认使用 Supabase 会偏离目标；只迁数据库连接却保留 Supabase Auth/PostgREST 也不算脱离。复用现有服务端能保留业务、权限、并发与幂等测试。

只存每日总数会丢失来源和修订证据；只存操作日志不能可靠重建库存。采用“原始批次/快照 + 版本化业务事实 + 可重算统计”，暂不引入数仓、ClickHouse、Kafka 或全系统事件溯源框架。

代价：需要承担认证安全、数据库备份/恢复、升级、同步进程和监控；历史存储增加，保留期与容量必须测算。无历史来源的时期仍为空缺，不承诺补出过去的趋势。

## 兼容与回退

保留商品、Variant、货票、用户 UUID 与人工货号。旧数据库及 00001–00052 作为基线，不原地改历史 Migration；目标库采用经校验的新基线和后续增量脚本。迁移前盘点所有 Supabase 依赖，隔离环境完成认证、RLS、同步与只读影子比对。

生产切换另获授权：冻结旧写入和同步、备份及恢复演练、记录最终水位、核对导入内容和权限、单点切流。写开放后失败须先停新写入并核对增量，再恢复旧系统；不能只回代码。观察期结束且明确批准前不删除旧环境。

## 验证门

- 新运行环境无 Supabase 服务地址、会话、SDK 或 service-role 凭证依赖；历史归档文件允许保留供应商名字。
- PostgreSQL 普通运行身份受 RLS/授权约束；停用、跨市场、空授权、金额拒绝、连接池串身份均测试。
- 历史重复/乱序/缺页/失败/晚到/更正可追溯；历史原貌和修订后口径可分别重现，日统计可幂等重建。
- 商品数量、在途和估值遵守原权威边界，不从库存差推算销量，不跨时间累加余额。
